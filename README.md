## 实现的主要链路

一个Raft对象表示一个节点，多个节点通过官方模拟网络交换RPC。实现按四条链路组织：

- **选举：** 选举到期进入新任期、自投票并拉票；处理回复时先承认更高任期，再过滤旧轮回复，达到多数派后成为领导者。
- **复制与交付：** 领导者接受命令后按跟随者进度构造请求；接收者核对前缀并修复后缀，领导者根据有效回复确认多数派提交，各节点再按顺序交付已提交命令。
- **保存与恢复：** 任期、投票或日志变化后编码保存；创建节点时先恢复协议状态和快照边界，再启动后台协程。角色及复制进度不作为这份持久化数据恢复。

- **快照与追赶：** 服务层生成已应用前缀的快照；Raft压缩日志并原子保存边界及快照，落后节点先安装快照，再复制后缀；唯一applier串行交付。

共享可变状态由节点互斥锁保护，网络等待和通道发送在锁外完成。复制回复与本机保留的原请求关联，成功进度只增不减，过时失败不能直接覆盖新进度。有副本、已提交、本机知道已提交、已交付是不同状态。

最新3D验收由学习者自行运行，七项官方测试全部PASS，包耗时266.158s，开启-race，未报告数据竞争。2026-10-05的旧阶段结果属于历史证据；快照改造后的回归已经通过，逐项结果单独记录在验收文档。

## 3C与3D学习疑问与回答

以下先保留四项持久化真实提问，再补七项快照学习疑问；完整3A～3D复盘见[真实疑问复盘](docs/learning-qa.md)。

### 3C：保存与重启恢复（实际疑问）

**24. 持久化这里的Go语法和API怎么用？能给一个例子吗？**（2026-10-04 23:24）

按“创建字节容器 → 创建编码器 → 按固定顺序编码状态 → 取得字节 → 交给保存容器”理解。bytes.Buffer负责容纳字节，labgob.NewEncoder负责把Go值编码进去，Encode返回的error要检查；编码成功后才能调用Persister.Save。恢复时反过来解码，Decode要传变量地址才能填写结果，读写顺序必须一致。完整实现保存在私有代码中。

**25. 为什么既有e又有w？它们分别干什么？**（2026-10-04 23:28）

w是存放编码结果的字节容器，e是向w写入数据的编码器：可以类比“装东西的盒子”和“把对象转换成字节的工具”。创建e不会自动保存字段，Encode才执行编码；w.Bytes取得结果，Save才把它交给官方保存容器。恢复时的容器装着旧字节，解码器从里面按顺序读取。

**26. tmp为空就不恢复吗？readPersist是自己实现，ReadRaftState是官方提供的吗？**（2026-10-04 23:39）

是。官方ReadRaftState取出此前保存的字节，自己的readPersist负责解释这些字节并恢复字段。首次启动没有保存数据，readPersist直接返回，保留Make初始化的任期、未投票标记和日志哨兵；有旧数据则先完整解码到临时变量再赋给节点。空数据与损坏数据不同，当前实现遇到解码错误会中断，不能静默当成首次启动。恢复完成后才启动后台协程。

**27. 所有修改votedFor、currentTerm、log的地方都要持久化，对吗？**（2026-10-04 23:41）

对，这三项需要跨重启保留。检查发现更高任期、发起选举并投给自己、授予选票、Start追加日志和AppendEntries修复后缀等路径；每次逻辑修改完成后，在依赖它的答复或消息对外生效前保存。可以在同一临界区完成一组修改再统一保存，不必每个赋值单独保存；日志没有变化的空心跳也不必因为日志再次保存。role、计票和复制进度不属于这三项持久化状态。


### 3D：快照与日志压缩（实际疑问）

**28. 为什么不每次都保存快照？取舍怎么算？**（2026-10-05～06学习期间，未记录精确提问时刻）

快照替代的是已经应用的操作前缀，保留快照后的日志；不是在初始值和操作之间任选一种。每次都生成快照会反复编码完整业务状态，增加保存和传输成本。间隔小，恢复重放少但生成频繁；间隔大，生成少但日志占用和重放增加。生产上根据状态大小、命令速率、快照耗时和恢复目标测量阈值；本实验服务约每10条命令触发快照，Raft只实现接口与协议，不替服务选择业务策略。

**29. 删掉1～80后，末尾任期和位置怎么计算？**

保留log[0]作为位置80的边界占位，保存它的任期，后面是81～100。末尾任期仍读切片最后一项，末尾全局位置是边界加切片长度减一；位置81的切片下标为1。投票、提交和RPC使用全局位置，访问切片时才减去边界。

**30. 为什么append一个空切片再加日志后缀？这是复制吗？**

以空切片为目标追加后缀，会分配独立条目数组，避免解锁后本机日志修改影响在途请求。末尾的...把后缀切片展开为条目参数。这是LogEntry值的浅复制，Command内部若包含指针或切片，其引用对象没有被深复制，仍要求命令内容保持不变。

**31. 前缀已压缩时，为什么领导者不能总要求nextIndex减一？**

B已压缩到80，A用起点51探测位置50，B只能提示从81重新核对。如果A仍取旧起点减一和提示的较小值，就走到50，越走越远。当前实现允许提示向前或向后改变探测起点，但仍过滤过时失败；提示不更新matchIndex，也不能据此提交，下一次还需核对边界任期并收到成功回复。

**32. 边界占位的Command是什么？Snapshot是不是服务层通知本机压缩？**

Command是业务命令。快照已经概括该位置及此前的执行结果，所以占位只留Term，Command为空，不能再作为命令执行。Snapshot是本机服务层提供快照，Raft切掉已覆盖前缀、保留后缀、更新边界并保存；InstallSnapshot才是另一节点发来的远程安装请求。边界位置与任期都匹配时保留本地后缀，否则舍弃旧日志后缀。

**33. 交付快照时为什么解锁，发送后又加锁？**

applyCh发送可能阻塞；持锁等待会让投票、心跳及快照接收都无法推进。唯一applier持锁取出待交付快照并清空槽位，解锁发送，再加锁记录已交付位置。时间线：取出S80 → 发送等待中收到S100并写入槽位 → S80发送完成 → 下一轮取出S100。不能在S80发送完成后再清空槽位，否则会删掉刚到的S100。lastApplied记录交付进度；在发送前推进属于另一种字段语义，并非仅凭这个动作就能断言协议错误。

**34. 快照请求为什么要独立副本？**

锁内复制快照字节，让解锁后的请求拥有稳定内容。协议要求在途数据不被并发修改，不要求只能靠复制实现；如果所有拥有者严格只读，也可以共享。当前采用复制明确所有权，新的本机快照替换数组，不原地修改旧消息。复制字节不等于复制全部业务对象。
